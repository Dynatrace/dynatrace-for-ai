glob-name-migrator

A command-line tool that rewrites Dynatrace global request naming rules so they no longer rely on conditions that are removed in Phase 3 of the cluster upgrade. It reads each existing rule, queries live data in Grail to discover replacement conditions that match the same services and endpoints, verifies the match is exact, and emits proposed replacement rules.

This document was written by reading the source under src/glob_name_migrator/. It describes what the code actually does; it is the only prose documentation the tool ships. All four commands, including run and apply, are fully implemented.

1. What problem it solves

A request naming rule decides how Dynatrace labels requests. Each rule has a list of conditions and an optional management-zones filter. Three condition kinds disappear in Phase 3 and must be replaced:

  • managementZones — the whole rule-level field.
  • SERVICE_TAG — always deprecated.
  • PROCESS_GROUP_TAG — deprecated unless every one of its tag keys starts with primary_tags.. A condition carrying only primary tags survives Phase 3 untouched. One that mixes a primary and an ordinary tag is not a valid rule at all — request naming cannot evaluate it correctly, validators block it, and a rule containing one is a product bug (see below). The migrator marks such a condition deprecated so the rule stays visible, then reports the whole rule unmigratable.

Primary tags are not a pass-through. They survive Phase 3, but are evaluated on the span side — against the entry-point span's primary_tags.* resource attributes with exact, case-sensitive string equality — not against the process-group entity's tag array. Three consequences run through the whole pipeline:

  • They are also candidate sources. The tenant's primary_tags.* span columns are discovered once per run (fieldsSnapshot spans) and projected into each rule's span query, so they can be scored as replacements for deprecated conditions. Emitted shape: PROCESS_GROUP_TAG + a TAG comparisonInfo carrying a TagDto.
  • Deduplication is key-level, not attribute-level. This is the surprising rule. For every other attribute, a surviving condition on it blocks it as a candidate. For primary tags, a surviving condition on primary_tags.team must not block primary_tags.stage — different keys are independent axes. Candidate identity therefore carries the key as a composite PROCESS_GROUP_TAG@primary_tags.team, split back apart only when the Config v1 body is written.
  • Scalar strings only. The runtime type-guards on String before comparing, so an array-valued (multi-value) primary tag can never match. Such a key is discarded as a candidate with reason array_valued — the key is dropped, never the rule.

Negation never occurs for a primary tag, in either direction. TagComparisonDto has no NOT_EQUALS, and the equivalent EQUALS + negate: true is refused too: MethodAttribute.PROCESS_GROUP_TAG declares isIndexCondition(), and ConditionSpecificationValidator.noNegationForMEIndex rejects negation on every ME-index attribute. Both have been in place since the Config v1 request-naming API was introduced (same commit, 2019-12-28), and that API is the only write path for a global rule with conditions — so a negated PG tag condition cannot exist in a tenant. The migrator therefore treats one as unmigratable on read, and fails loudly rather than emit one. (Note for backend readers: NamingRuleEvaluation does carry a negated flag on its PgTagCondition and applies it, but no rule can be created that sets it — that branch is unreachable.)

A condition mixing a primary and an ordinary tag in one any-of is not supported by request naming and is being blocked at the API — such a condition means "PG tagged team:ck or span carrying primary_tags.env=prod", a disjunction across an entity attribute and a span attribute that neither the runtime nor this pipeline can express (both AND their entity- and span-side evaluation). It therefore has no well-defined set of matched services — not just for the migrator to reproduce, but for the feature itself: request naming cannot evaluate such a condition correctly either. Validators prevent it from being created, so a rule that contains one is a bug in the feature, not an input the migrator should try to interpret. The migrator classifies it as deprecated, so the rule is never silently skipped as "nothing deprecated", and then reports the whole rule unmigratable (any unmigratable condition stops the rule before the query stage) with a reason telling the customer to rewrite it. No automatic migration is planned.

The migrator's job: for every rule that uses a deprecated condition, find a set of surviving attributes (URL path, application name, service type, endpoint name, …) whose values — read from real entities and spans — select exactly the same services and endpoints the original rule did. If it can, it writes out a ready-to-POST replacement rule. The original is never changed by run.

3. Configuration & auth

Resolved in config.py. Two host URLs are tracked because the classic Config v1 API and the platform DQL API usually live on different domains:

  --tenant https://abc.dynatrace.com
        │
        ├─ classic_url  →  https://abc.dynatrace.com            (Config v1 REST)
        └─ platform_url →  https://abc.apps.dynatrace.com       (DQL storage query)

  Only one URL is needed; the other is derived by inserting / removing
  the ".apps." infix. Either can be overridden with --classic-url / --platform-url.

A single platform token (dt0s16.*) is used for both APIs — sent as an Api-Token header to Config v1 and as a Bearer token to the storage query API. The token must carry ReadConfig + storage:*:read scopes (and WriteConfig for apply). Classic dt0c01.* tokens are rejected. The token is masked in AppConfig.__repr__ so it can't leak into logs.

Flags fall back to env vars: DT_TENANT, DT_CLASSIC_URL, DT_PLATFORM_URL, DT_PLATFORM_TOKEN, GNM_OUTPUT_DIR. The output directory defaults to a timestamped ./workdir/run-YYYYMMDD-HHMMSS/.

4. The pipeline at a glance

orchestrator.run() drives everything. It lists the target rules, then runs each one through the same per-rule pipeline, and finally writes an aggregate summary and HTML report.

                        ║  2. SKIP if disabled                        ║

Two early skips keep the run cheap: disabled rules are dropped unconditionally, and enabled rules whose conditions are all surviving (no deprecated condition) are dropped after a fast classification probe — they need no migration. Both are recorded in the summary so nothing silently disappears.

A rule only reaches the query/candidate/verify stages if every condition translated successfully (unmigratable_count == 0) and a DQL client is available. If any condition is unmigratable, the rule stops after the sidecar with its reasons recorded.

5. Classification — Case A / C

rules/classifier.py sorts a rule's conditions into a 2×2 grid — entity-side vs span-side (decided per condition by condition_side(), which consults the attribute mapping and, for PROCESS_GROUP_TAG, the tag keys themselves) and surviving vs deprecated — and then assigns a case based on where conditions live:

CaseWhere conditions liveConsequence for querying
AEntity-side only (incl. a non-empty managementZones)Entity query only; span query is a fallback
CBoth entity-side and span-sideEntity query first, span query second

Only Cases A and C are migratable: every Phase-3 deprecated condition (managementZones, SERVICE_TAG, non-primary_tags. PROCESS_GROUP_TAG) is entity-side, so any rule that needs migration always carries entity-side content. A span-only rule is therefore never deprecated and is skipped before any case-dependent code runs. An attribute whose mapping is unknown is treated as entity-side so it stays visible to later stages. The one exception is the mixed primary/ordinary PG tag condition described in §1: it is both deprecated and span-side, so a rule containing nothing else is a deprecated Case C rule with no entity-side content — harmless, because it is unmigratable and stops at the sidecar before any case-dependent code runs.

Primary tags shift the case. Because a surviving primary_tags.* condition is span-side, a rule whose only non-managementZones condition is a primary tag classifies as Case C, not A — it cannot be verified without a span query. Case C consequently tolerates a rule whose span side holds only surviving conditions, with no deprecated span condition at all. Side is decided per condition by classifier.condition_side(), which is also what cache.split_conditions() uses: PROCESS_GROUP_TAG is a single mapping row serving both primary and ordinary tags, so if the two disagreed, the sidecar would file a condition span-side while the cache key filed it entity-side, silently sharing cache entries between rules that are not equivalent.

Cache keys

cache.py derives two stable keys per rule, each a SHA-256[:12] of canonical JSON (keys sorted recursively, lists sorted by element):

  • entity_key — over managementZones + the entity-level conditions.
  • span_key — over entity_key + the span-level conditions.

Two rules with the same entity shape share cached entity rows; same entity and span shape share span rows too. Cache files are named after these keys, so re-runs are idempotent and rules with identical shapes don't re-query.

6. Translation to DQL

rules/translator.py turns one Config v1 condition into one DQL filter fragment — a pure function. Each result is a Translation carrying either a DQL string or an unmigratable_reason.

  Condition                                  DQL fragment
  ─────────────────────────────────────────  ─────────────────────────────────────
  STRING EQUALS "foo"                    →    key == "foo"
  STRING BEGINS_WITH "foo"               →    startsWith(key, "foo")
  STRING EQUALS_ANY_OF [a,b]             →    in(key, {"a", "b"})
  NUMBER GREATER_THAN 5                  →    key > 5
  BOOLEAN EQUALS true                    →    key == true
  APPLICATION_* (array<string>)          →    in(key, {"v"})        (array idiom)
  TAG EQUALS {key,value}                 →    matchesValue(tags, "*key:value")
  TAG_KEY_EQUALS "k"                     →    matchesValue(tags, {"k", "k:*"})
  HTTP_STATUS_CLASS C_4XX                →    http.response.status_code div 100 == 4
  IS_KEY_REQUEST == false                →    ...is_non_key_requests... == true
  managementZones [z1,z2]                →    matchesValue(managementZones, {"z1","z2"})
  negate=true                            →    not ( ... )

  REGEX_MATCHES, REQUEST_ATTRIBUTE,      →    UNMIGRATABLE (reason recorded)
  ONE_AGENT_ATTRIBUTE, IS_KEY_REQUEST==true

The translator also enforces per-attribute restriction tables: some attributes forbid negation, some forbid EXISTS. A violation makes the condition unmigratable rather than producing wrong DQL. It deliberately does not add the isExternalService != true pre-filter or projection lists — those belong to the query builders.

7. Querying live data

query_executor.py issues the entity and span queries, dispatching by case. The goal of this stage is to compute the rule's original target sets from live data:

  • S_super — services matching the rule's entity-side conditions.
  • S_orig — the services that actually have matching endpoint spans.
  • E_orig — the (service, endpoint) pairs matched by the rule.
Case A  (entity only)
  A.1  fetch dt.entity.service | filter <svc conds> | fields id, serviceType, …
            → S_super   →  cache/<entity_key>_s_super.json

Case C  (both)
  C.1  fetch dt.entity.service | filter <svc conds>        → S_super
  C.2  fetch spans | filter <span conds> and in(service, S_super_ids)
            → E_orig, S_orig

  PG branch:  if conditions target process groups, the entity step runs a
              two-query plan — fetch process_group ids first, then substitute
              them into the service query (in(runs_on[...], {PG ids})).

  A.2 fallback:  see below.

The entity query always projects id + serviceType plus every candidate-eligible service attribute (so the next stage has columns to mine). The span query groups by dt.smartscape.service + endpoint.name plus every candidate-eligible span key, and adds a synthetic dt_webrequest_url column reconstructed from server.address + optional :port + url.path.

Span retry. Spans are short-lived. In Case C, if the constrained span query returns nothing, the executor retries with time-shifted windows (up to 3 attempts, each stepping ~6 h further back) before giving up with rule_matching_no_data. Read-limit and other DQL errors abort just that rule and are recorded as a failure_reason.

Case A span fallback (A.2)

A Case A rule has no span conditions, so normally only the entity query runs. But if entity-side scoring (§8) finds no usable candidate, the orchestrator runs an extra no-condition span query constrained to S_super's service IDs, re-derives S_orig/E_orig from the spans, and re-scores in full mode. This rescues Case A rules that can only be distinguished at the endpoint level.

8. Finding replacement candidates

analysis/candidates.py is pure post-processing of the cached rows — no new DQL. For every column in the result it asks: "could a filter on this attribute replace the deprecated condition?"

  for each DQL column in the cached rows (excluding structural id/service/endpoint):
       │
       ├─ resolve column → API attribute   (scope-aware: may depend on serviceType)
       │
       ├─ DROP if attribute is a surviving condition already      (no point)
       ├─ DROP if attribute is unmigratable-as-candidate
       ├─ DROP if any row has a null value for this column        (would under-match)
       │
       └─ count distinct values:
              1 distinct value      →  kind = "full"            key == "v"
              ≤ partial_cap (5) and
                matcher supports ANY_OF  →  "partial_promoted"  in(key, {v1,v2,…})
              > cap or no ANY_OF     →  DISCARD (recorded with reason)

  → sort (full before partial), de-duplicate by value-set (entity side wins)
  → entity_candidates[] , span_candidates[] , discarded_for_report[]

Scope-aware resolution

Some DQL keys map to different API attributes depending on the service's type (e.g. web vs. messaging). resolve_api_attribute() consults the mapping's scope partitions and a per-service serviceType index; depending on the configured mixed_behavior it picks a default, lets the narrower type win, or marks the column unmigratable when types are mixed across rows.

Substring rescue

analysis/substring_candidate_rescue.py then augments the artifact. When a string column has several distinct values, an exact match won't generalise — so it looks for a shared longest common prefix (→ BEGINS_WITH) or suffix (→ ENDS_WITH), each at least 4 characters. As a last resort, if no candidate of any kind exists on either side, it tries a shared longest common substring (→ CONTAINS). These are tagged substring_full.

Good vs. suboptimal

Each candidate's quality comes from the mapping (good or suboptimal). The verification loop starts with good candidates only and keeps the suboptimal ones as an escalation pool.

9. The overselect verification loop

analysis/overselect_loop.py is the heart of the tool. It drives a state machine to a terminal verdict, running real DQL queries (cached per filter+window) and comparing the candidate filter's result against the original target sets. The principle: a replacement is only valid if it selects exactly what the original did — not more (over-select), not less (under-select).

When span data exists the loop runs in two phases; an entity-only rule runs just the first.

  ┌─ PHASE 1 · ENTITY PRE-PHASE ────────────────────────────────────────┐
  │  run entity query with entity candidate + surviving fragments       │
  │  compare matched services  S_cand   vs   S_orig                     │
  │                                                                     │
  │     S_cand == S_orig   →  EXACT   → service_filter = S_cand ✓        │
  │     S_cand  ⊂ S_orig   →  UNDER   → drop filter, let span phase cover│
  │     S_cand  ⊃ S_orig   →  OVER    → greedy negation, retry           │
  │                                     (exhausted → keep as filter)     │
  └─────────────────────────────────────────────────────────────────────┘
                                  │  service_filter
                                  ▼
  ┌─ PHASE 2 · SPAN LOOP ───────────────────────────────────────────────┐
  │  run span query with span fragments + in(service, service_filter)   │
  │  compare (S_cand, E_cand)  vs  (S_orig, E_orig)                      │
  │                                                                     │
  │     exact               →  ✅ EXACT_MATCH                            │
  │     under-select        →  shift window earlier & retry (≤1×)        │
  │                            then accept as best-effort                │
  │     over-select         →  escalation ladder ↓                       │
  │                                                                     │
  │        1. greedy set-cover NEGATIONS (not key == "v")               │
  │           — only applied if they fully cover the excess rows        │
  │        2. SUBSTRING DEMOTION — turn a BEGINS_WITH candidate back     │
  │           into in(key, {exact values}); reset & retry               │
  │        3. SUBOPTIMAL ESCALATION — add one suboptimal candidate;      │
  │           reset & retry                                             │
  │        4. all exhausted   →  ❌ NO_REPLACEMENT                        │
  └─────────────────────────────────────────────────────────────────────┘

Greedy negation

When the candidate filter matches a few too many rows, the loop finds attribute=value pairs that appear only in the over-selected rows (never in legitimate rows) and adds them as negations — choosing the pairs that drop the most excess rows first (a single-pass set cover), bounded by a per-attribute cap (default 5) and the mapping's "negation forbidden" list.

Terminal verdicts

VerdictMeaning
exact_matchCandidates select exactly S_orig / E_orig.
exact_match_after_under_select_retryExact after a window shift, or accepted best-effort when only under-selecting remained.
no_replacementOver-select could not be resolved by any negation / demotion / escalation (refinement_exhausted or substring_demotion_exhausted).

The verdict — including the final condition list, the negations, the demotions, and the full iteration history — is written to derived/<rule_id>_verdict.json. A safety guard turns a 0-row verification query into a hard error, because by construction the candidate filter must match at least the original set.

10. Reports & output

report/builder.py assembles a per-rule report from the sidecar, the candidates artifact, and the verdict. Its most important output is replacement_rule_body — a complete Config v1 RequestNamingDto built by copying the original rule, emptying managementZones, and replacing conditions with the verified ones (candidate conditions reconstructed into comparisonInfo objects, negations emitted as NOT_EQUALS, surviving conditions copied verbatim). This body is what apply later POSTs.

report/html.py reads all per-rule reports and writes a self-contained report/report.html that buckets rules into:

✅ Replacement foundexact match — including those reached only after negations / demotions / window retry (the per-rule neg/dem counts remain visible in each rule's detail)
⚠️ No safe replacementno replacement found — manual migration required
⏸️ No traffic datarule not observed in live traffic across the queried windows
💥 Failuresa stage errored out

Empty buckets are omitted entirely (no zero-count rows), and the summary table links to each populated section.

  <output-dir>/

  │                 <span_key>_s_orig.json      <verify_key>_verify_{e,s}.json

  │                 <id>.json  <id>_candidates.json  <id>_verdict.json

11. The apply command — uploading replacements

upload_replacements.py takes a finished run workdir (--run-dir) and pushes the discovered replacements to the tenant. It is the only part of the tool that writes to Dynatrace.

  read report/summary.json  → rules whose verification_status is an exact match
  read report/<id>.json      → replacement_rule_body for each
        │
        ├─ list live rules (Config v1) — validate the original still exists
        ├─ skip rules with no replacement / original missing
        │
   for each target:
        └─ POST replacement as a DISABLED rule        → new rule id
        │
        ▼
   reorder ALL rules so each new rule sits directly ABOVE its original
        │
        ▼
   write report/apply_log.json

Replacements are uploaded disabled and placed just above the original in the global evaluation order — so a human can review and enable them. Originals are never modified. If the POSTs succeed but the reorder call fails, the tool raises ApplyReorderError listing the new rule IDs that need manual reordering, and still writes the apply log.
